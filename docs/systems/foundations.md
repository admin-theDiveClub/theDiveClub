## Data architecture
- One Supabase project for everything, never one project per venue.
- **`tbl_players` is the hub.** One row per person, with or without a login:
  - `user_id` links to `auth.users`. It can be empty and is unique. It's empty for guests and for walk-ins who haven't signed up.
  - `player_type` is `member`, `walk_in` or `guest`. `guest_of_player_id` records whose guest someone is.
  - Signups create a `member` row automatically (trigger). A walk-in claims their existing row later, through the identifiers step.
  - Only non-private info goes here (display name, first and last name), and all signed-in users can read it.
- **Private identifiers** (SA ID, passport, phone, email) go in a separate protected table, never in `tbl_players`.
  - Verification belongs to the ID, and is done in store by staff (verified_by, verified_at).
  - Blocking rules per business track are enforced in the database, not only in the UI. Cannabis: everything is blocked until verified. Pool: league entry requires verification.
- Domains:
  - **Global:** Identity, Ranking & Competition (WST-style points), Gamification (XP, raffles, fantasy league, hall of fame, top trumps).
  - **Venue-scoped via `venue_id`:** Commerce (closed-loop credits, working name "Cuedits"), Venue Ops (bookings, stock, table scheduling).
  - **Cross-cutting:** Platform (audit log, roles).
- Commerce and Ranking never share tables. `player_id` on a transaction is nullable (cash sales with no linked member are valid).

## Reading fast (16 Nov)
Each trip to the database is about a quarter of a second from Johannesburg (eu-west-1), so **a page sends every read it can at once, and never waits for one it does not need the answer of** (UV, 16 Nov: "as fast loading as possible").
- **`TDC.readEarly(key, make)` and `TDC.read(key, make)`** (`tdc.js`). A page starts the reads it will need together (`readEarly`); each loader takes its own (`read`) when it gets there, in the order it always ran, so what is drawn and when is unchanged: only the waiting overlaps. A read nobody started, or one older than 10 s, is made fresh, so a write's re-read never gets a stale answer. Keys are the page's own (`season:fixtures`). The usual shape, in each tab script: a `Q` object defining each read once, `take(key)`, and `startReads()` called at the start and at the top of `loadAll` (with `loadAll(true)` from the start, so they are not sent twice).
- **A supabase query is sent only when something waits on it.** To start one early, wrap it: `Promise.resolve(supabaseClient.rpc(...))` (`readEarly` does this).
- **Short links:** `TDC.shortKey(kind, id)` / `TDC.shortRead(kind, id)` let a page start the short link early; `TDC.shortUrl` and the short-code field take it.
- **A read that waits on another is the costly kind.** Where a page needs one call per thing in a list it has to read first, one call for the whole list that needs only what the page already knows takes the second trip away: `tdc_league_season_rosters(season)` (`20261117041517`, 17 Nov) answers every team's roster at once, sent with the Season tab's first batch, in place of `tdc_team_roster` once per team after the team list. The card still reads its two rosters with `tdc_team_roster`.
- **Measured on production (17 Nov, read-only):** every call costs about 0.2 s however little it does (even `tdc_record_device`, 15 ms of work: 0.2 s typical), the trip to eu-west-1. `tdc_league_fixtures` does 40 ms of work for 132 fixtures and is 0.23 s typical; the 1.8 s in UV's 16 Nov trace was a one-off. So the gain is in fewer trips, not faster functions. Production's request log (`edge_logs`, `response.origin_time`) gives each call's time.
- Shared helpers ask their reads together: the venue picker (the list and the chosen venues), the standings editor (variables and columns), the card's rosters and its six card reads, the profile's balances.
- **Done 16 Nov:** the league Season, Fixtures / Schedule, Run it and Settings tabs, the card, the profile. Measured headless at 420px, the CPU 4× slower and 220 ms added to each trip, signed in as a league director on a local copy of 8-Ball Mainstream: Season 3.9 → 1.9 s to the diver lifting, the card 4.1 → 2.1 s, Run it 3.1 → 1.5 s, Settings 2.7 → 1.7 s, the profile 2.2 → 1.0 s, Fixtures 1.8 → 1.1 s; every page's text identical before and after. The measuring script is not in the repo (it needs stand-in accounts on the local copy); `docs/STATUS.md` says what is left.

## Venues (migration `20261105200430`, 5 Nov; step 1 of 3: the database. Step 2, the picker, below. Step 3 is to come)

**A competition has two kinds of venue, kept apart on purpose.**

| | Belongs to | Played at |
|---|---|---|
| Held in | `venue_id` on `tbl_leagues`, `tbl_tournaments` | `tbl_league_season_venues`, `tbl_tournament_venues`, `tbl_league_fixtures.venue_id` |
| Gives | Its staff run it; its credits settle there | Nothing: words on a page |
| Who chooses | The venue's owner or admin (tournaments allowed staff until 17 Nov) | Whoever runs the competition, from the active venues they own or admin (17 Nov; any active venue before). One already on the list may stay |
| Changes | Fixed at creation | Any time |

- **`tbl_matches.venue_id` is a rights column.** A match copies what its competition belongs to, and `private.tdc_can_edit_match` lets that venue's staff edit the card. A played-at venue must never be written there, or a barman at a club hosting one night could change a league's scores.
- **Only a venue's owner or admin may choose it (UV, 17 Nov; migration `20261117073856_venue_owners_choose`).** Everywhere a venue is selected: a player, another venue's owner, or the venue's own staff may not. For played at, `private.tdc_check_venue_list` (which the season list, the tournament list and both fixture writers call) refuses a venue the caller does not own or admin, unless it is already on that list. Already listed means kept, as a closed venue is, so an old season still saves, and a new season's copy of the list (done by `tdc_create_league_season` itself) keeps it. Once taken off, only the venue's owner or admin can put it back. **The site owner may choose any venue (UV, 24 Nov; migration `20261124145529_site_owner_chooses_venues`)**: the test is now `private.tdc_can_choose_venue`, the one place (owner or admin, or the site owner), and `tdc_check_venue_list` asks it. Rick Schoenlank owns both Billiard Cafés (same migration), so 8-Ball Mainstream's Rivonia listing has an owner. **The staff pages** (walk-in, credits, codes, verify, link) still offer the venues where you are owner, admin or staff: they choose where you work, not what a venue is tied to.
- **Credits (17 Nov):** `tbl_venues.sells_credits`, on for The Dive Club only. The profile's Credits section lists only those venues (UV: a business operation; no other club is shown there yet). Set by migration.
- **The picker (`scripts/venue-picker.js`, `TDCVenuePicker`, step 2):** a search box that adds each venue as a pill, for the played-at list only, on `/tournaments/new/`, `/leagues/new/` and both Settings tabs. It filters `tdc_venues()` in the browser with no call, by name, area and city, keeping only the venues `tdc_choosable_venues()` sends, read alongside (their own as owner or admin; every open venue for the site owner; 24 Nov, before which the page read its own `tbl_venue_staff` rows and decided itself). For the site owner the field still says "Search your venues"; with none, the field says "You don't own or run a venue" and is disabled. A pill already on the list can still be removed by anyone running the competition. The order is the order added. The list is saved by its own call after the rest, and only when it changed, so an old competition is never rewritten by an unrelated save. A closed venue is not in `tdc_venues()` and cannot be named by someone who is not its staff, so it keeps a pill reading "A closed venue": a save that left it out would take it off without anyone choosing that. A new season starts from the last season's list, closed venues left out, which is what `tdc_create_league_season` copies; the list is sent only if the person changed it. On a create page the competition exists by the time the venues are saved, so a refusal leaves the button off and links to Settings rather than letting a second press make another. **The venue a competition belongs to has no picker yet: `p_venue_id` is still always null.** Nothing shows the played-at list yet; the season banner and the poster still read the belongs-to venue.
- **Played-at is per season**, so a league moving club does not rewrite its old seasons. `tdc_create_league_season` copies the last season's list, less any venue since closed. `tdc_set_league_season_venues` and `tdc_set_tournament_venues` take the whole list in order; empty clears it. A venue that closed while on a list may stay on it.
- **A fixture** may name its own venue (`p_venue_id`, `p_clear_venue` on `tdc_set_league_fixture`; `p_venue_id` on `tdc_add_league_fixture`). `tdc_league_fixtures` returns `venue_id`, `venue_name` and `venue_inherited`: its own, else the season's when the season has exactly one. A blank fixture in a season at several returns none, so the page lists the season's rather than sending a player to the wrong club.
- **Details on `tbl_venues`:** description, address, area, city, maps_url, picture_path, table_count, table_note, phone, whatsapp, email, website_url, instagram_url, facebook_url, hours_note. Links must be https, which keeps a `javascript:` address off public pages.
- **Hours are `tbl_venue_hours`:** one row each time the venue opens (`day_of_week` 1 is Monday, 7 Sunday; `opens_at`, `closes_at`). No row is closed. A closing time earlier than the opening time is the next morning. **Since 17 Nov `tdc_set_venue_hours(venue, jsonb)` writes them**, the whole week at once from the Settings tab (below); before that UV typed them in the dashboard.
- **Reading:** `tdc_venues()` (the active list) and `tdc_venue(id)` (one venue with its hours) are the only way in for someone signed out; `tbl_venues` is not granted to `anon`. Display details only.
- **Editing:** `tdc_update_venue` (the whole form at once, so a blank clears), `tdc_set_venue_picture` and `tdc_set_venue_hours`. **Who may: `private.tdc_can_edit_venue`, the one place** (17 Nov): the venue's owner or admin, or **the site owner**, The Dive Club's owner (admin@thediveclub.org in production, not UV's personal account, which is staff there), the same test as the title ladder. The picture bucket's write rules ask it too. The site owner's exception was **details only** (17 Nov): tying a competition to a venue still takes that venue's own owner or admin, but since 24 Nov the site owner may list any venue as played at (UV; `20261124145529_site_owner_chooses_venues`). Name, slug, timezone, currency and active are not editable (UV, 17 Nov: the name stays in migrations). **New venues come through a migration.** Nobody but the site owner can edit a venue with no owner, and nobody can tie a competition to it or list it as played at (17 Nov).
- **Picture:** the public `venue-pictures` bucket, `<venue id>/<random>.webp`, built as `team-pictures` is.
- **Where a venue is shown (migration `20261105203829`, 5 Nov; step 3).** Everything shows where a competition is **played**, as `[{ id, name }]` in the director's order: a `venues` column on `tdc_my_leagues`, `tdc_search_leagues`, `tdc_league_season_info`, `tdc_my_tournaments` and `tdc_open_tournaments` (their old `venue_id` and `venue_name` still mean what it belongs to, and no page reads them now); `venues` in the poster's snapshot and on a profile's teams and matches; `tdc_tournament_venue_list(id)` for pages reading the tournament's own row; `tdc_match_venue_list(id)` for one match: a fixture's own venue, else the season's list, a tournament's list, or a social match's venue. Changing a tournament's list rebuilds its poster, if it has one, with the choices it already has, since Settings saves the list after everything else.
- **Drawn by four helpers in `tdc.js`, so every page reads the same:** `venueNames` (words, on a card that is itself a link), `venueLink`, `venueHeading` (a heading's line) and `venueFact` (a banner's row, a line each, null with none). With no venue the row is left out everywhere. The banner on a match counts several ("3 venues").
- **A venue's page** (`/venues/?v=<id>`, `scripts/venue.js`): renders signed out, because the poster links to it. Reads `tdc_venue` and `tdc_venue_competitions`, the second listing what belongs to the venue, is played at it, or (leagues) has a fixture there, and only what is listed. A league opens its join page; a tournament its poster until it starts, then its draw. Those but the poster ask a stranger to sign in.

- **The drawing** (`_includes/install/safari.svg`, included into the page): every screen redrawn in SVG from UV's iOS 26 screenshots, in the iPhone's own 390 × 844 points. Contacts, apps, the widget and the wallpaper are plain shapes; the clock always reads 16:20 and the battery 80. It points at the site's own `apple-touch-icon.png` (the icon iOS really uses: see-through, so the share sheet shows it on white and the home screen on black, as on a real phone), `icon-primary.svg` and `logo-primary-dark.svg`, so **a new icon or logo arrives by itself**. The site's home page is one block, `#ins-tdc-home`: **when the home page changes, redraw that block**. Every id starts `ins-` and every class `i-`, so the site's styles never reach it.
- **The drawing follows the theme** (UV, 3 Nov): iOS in dark mode in the dark theme, in light mode in the light theme. Every colour in it is a token in `install.css` (`--ios-*` for the iPhone, `--ins-*` for the site's screen, whose band, rings, words and button use the site's own `--bg-base`, `--color-primary`, `--text-primary`), written into the SVG as inline styles, never as `fill="var(…)"` attributes (a presentation attribute is not sure to read a variable in every browser). Seven colours are fixed on purpose, the same in both: the white tiles behind app icons, the toggle's knob, the white words on the blue Add and the site's button (as the real page has), the black dim and the black under the home-screen icon. The app icon stays the dark one in both: a phone's home-screen icon does not follow a site's theme. Checked 3 Nov: the dark theme's phone pixel-identical to before at 24 moments of the loop; the light theme looked at through every step.
- **The animation** (`scripts/install.js`): the timeline is a set of numbers keyed in time (the finger's position and press, how far the keyboard, menu, sheet and dialog are in, the toggle, the icon's pop), eased between keys; `render(t)` draws any moment from them. That is what lets a tap on a step jump straight to it and the loop restart cleanly. A flat dot in the site's green is the finger: it moves, taps (a ripple), drags the sheet up by its header (never on a button) and types the address one key at a time. **The finger's points are coordinates in the drawing**: move a button in the SVG and move its point in the timeline with it.

- **Full and Compact**, switched by the pill beside Play and animated between (the View Transitions API; instant where the browser has none or with less motion). **Compact** is for following along on the phone itself: an 84px-wide screen and the live step beside it, held under the nav (`position: sticky`), the heading folded away so the block sits right under the nav (the page is too short to scroll it there). The list scrolls so the live step sits at the top of its window. The page opens in Full until switched (UV); the choice is kept on the device (`tdc.install-mode`).
- **Less motion** (the profile menu's toggle or the phone's setting, `TDCPrefs.lessMotion`): the animation waits for Play.

## Full names: the surname lighter (12 Nov)

**The rule (UV, 12 Nov):** wherever a player's first name and surname are shown, the surname is drawn at **400** and the first name keeps the weight of whatever holds it (600 in a Standings row, 700 on a won draw card). **Display names are never split**: a display name is the player's own choice and often a nickname. Where a full name already sits at 400 (a muted sub-line under a display name), nothing looks different; the markup is there so the rule still holds if that line's weight changes.

**How:** `TDC.fullName(full, surname)` in `tdc.js` returns a fragment, the first name as text and the surname in `<span class="tdc-surname">` (`global.css`). `TDC.fullNameOf(first, last)` does the same from a row's two names. Both go in with `append` / `replaceChildren`, never `textContent`. If the surname does not end the full name (both come from the same row, so it should never happen) the name is drawn whole and `[Names]` goes to the console.

**Why the surname comes separately:** the server joined first name and surname into one `full_name` string, and splitting it again at a space is wrong for a first name such as "Mary Anne". Migration `20261112152540_surnames_apart` adds `surname` beside `full_name` to every read that sends one: `tdc_search_opponents`, `tdc_search_entrants`, `tdc_search_league_players`, `tdc_search_referees`, `tdc_my_follows`, `tdc_league_standings` (each player), `tdc_player_profile` (the player), and `home_surname` / `away_surname` at the end of `tdc_tournament_draw`. The table-returning ones were dropped and created again (patched from a freshly reset database's text, their grants and comments restored); the two jsonb ones were replaced in place. It is called `surname`, not `last_name`, so an output column can never be confused with `tbl_players.last_name` inside the function. Reads that already sent `first_name` and `last_name` (the entrant lists, the nav's own player, `/match/`'s players, the staff search) use `fullNameOf`. Test: `074_surnames_apart`.

**Where it is drawn:** the Standings and draw Full names switch (and the draw's entrant pills), league and tournament management's player searches and the league's entrant lists, the opponent and referee pickers, `/match/`'s players, the player profile (header, About, Compare, Find, Following), the profile menu's banner, the staff pages' player line, and the walk-ins on a profile.

**A limit:** `TDC.liveFade` skips an element that holds other elements, so a full name in the draw does not fade when its slot changes; the display name still does.
